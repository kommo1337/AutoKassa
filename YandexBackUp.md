# 1. Резюме

Проверена реализация плана `YandexBackUp.md`: OAuth 2.0/PKCE, DPAPI-хранилище токена, REST-клиент Яндекс Диска, локальная очередь, подтверждение выгрузки, ротация, планировщик, настройки, миграция, UI, DI, тесты и документация.

**Общий вывод:** большая часть функциональности присутств и основной сценарий выгрузки реализован достаточно аккуратно. Однако есть несколько существенных дефектов:

- ротация читает неправильную структу ответа API и на реальных ответах получает пустой список;
- после исправления чтения списка ротация сможет безвозвратно удалить папку с подходящим именем, поскольку тип ресурса игнорируется;
- после неудачного обмена OAuth-кода UI может не позволить повторить подключение без перезапуска приложения;
- повреждённый файл очереди брочно блокирует создание новых облачных копий;
- ошибки чтения метаданных и HTTP-таймауты обрабатываются не в соответствии с планом.

**Функциональность пока нельзя считать готовой к production.** Сначала необходимо исправить YD-01–YD-05 и провести живой сценарий с тестовым аккаунтом.

## **[YD-01] Ротация не отличает файлы от папок — P0**

- **асположение:** `AutoKassa/Services/Backup/YandexDisk/YandexDiskBackupService.cs:325-347`, `AutoKassa/Services/Backup/YandexDisk/YandexDiskDtos.cs:54-74`, `AutoK/Services/Backup/YandexDisk/IYandexDiskApiClient.cs:16-18`
- **Уверенность:** высокая.
- **Суть:** API возвращает `type: "file"` или `"dir"`, DTO поле получает, но `DiskResourceInfo` его отбрасывает. Ротация фильтрует только имя и вызывает удаление с `permanently=true`.
- **Почему неправильно:** п разрешает удалять только **файлы** `AutoKassa_Backup_*.db`. Папка с таким именем не должна считаться управляемой резервной копией.
- **Сценар:** пользователь создаёт в `app:/` старую папку `AutoKassa_Backup_archive.db`; после появления достаточного количества копий она попадает за пределы `BackupKeep` и удаляется вместе с содержимым.
- **Последствия:** безвозвратная потеря данных в папке приложения.
- **Важное условие:** сейчас рискскируется YD-02 — реальный список ресурсов читается как пустой. Но исправление YD-02 без проверки типа немедленно откроет этот путь пот данных.
- **Минимальное исправление:** сохранять `Type` в `DiskResourceInfo` и пропускать только `Type == "file"`.
- **Долгосрочное решение:** дополнно проверять точный формат имени с датой, например `AutoKassa_Backup_yyyyMMdd_HHmmss.db`, а не любой suffix `.db`.
- 

```csharp
public sealed record DiskResourceInfo(
    string Name, long Size, string? Md5, DateTime? CreatedUtc, string? Type);

var managed = resources
    .Where => r.Type == "file" && IsManagedBackupName(r.Name))
    .ToList();
```

- **Тест:** вернуть папку `type:"dir"` с именем, подходящим под маску, и нескольколов; убедиться, что DELETE для папки не выполняется.

## **[YD-02] Неверный разбор списка ресурсов — P1**

- **Расположение:** `AutoKassa/S/Backup/YandexDisk/YandexDiskApiClient.cs:113-141`, `AutoKassa/Services/Backup/YandexDisk/YandexDiskDtos.cs:83-101`
- **Уверенность:** высокая.
- **С:** клиент десериализует верхнеуровневый `items`. По [официальной документации Яндекс Диска](https://yandex.ru/dev/disk-api/doc/ru/reference/meta) содимое папки находится в `_embedded.items`.
- **Почему неправильно:** `payload.Items` для реального ответа остаётся `null`, заменяется пустым списком, ц завершается после первой страницы.
- **Сценарий:** загрузить больше копий, чем `BackupKeepCount`; после успешной выгрузки ротация получает пустой спок и ничего не удаляет.
- **Последствия:** не выполняется пункт плана о ротации; файлы и занимаемое место накапливаются.
- **Минимальное исправ:** добавить DTO для `_embedded` и читать `payload.Embedded?.Items`.
- **Долгосрочное решение:** использовать также `_embedded.total` для контроля полноты чтения и запраивать только необходимые поля.
- **Альтернативы:** сторонний SDK здесь не нужен — исправление DTO значительно проще и не добавляет зависимостей.

```csharppublic sealed class DiskResourceResponse
{
    [JsonPropertyName("_embedded")]
    public DiskResourceListResponse? Embedded { get; set; }
    // name, type, md5, size, created...
}

var payload = await ReadJsonAsync<DiskResponse>(response, ct);
var items = payload.Embedded?.Items ?? new List<DiskResourceResponse>();
```

- **Тест:** заменить фикстуру в `YandexDiskApiClientTests.cs:84-109` на реальныйembedded.items`, проверить 100+1 элементов, пустую папку и отсутствие `_embedded`.

## **[YD-03] Невозможно повторить OAuth после ошибки — P1**

- **асположение:** `AutoKassa/Services/Backup/YandexDisk/YandexDiskAuthService.cs:113-125`, `AutoKassa/ViewModels/SettingsViewModel.cs:749-753,809-839`
- **Уверенность:** высок.
- **Суть:** сервис удаляет `_pending` перед сетевым обменом. При ошибке ViewModel оставляет `CloudAwaitingCode=true`, а `CanConnectYandex()` в этом состоянии запщает новое подключение.
- **Сценарий:** нажать «Подключить», ввести неверный/просроченный код или получить сетевой сбой. Сервис ощает попытку; кнопка «Подключить» остаётся недоступной. Повторный «Подтвердить» лишь сообщает, что активной попытки нет.
- **Последствия:** первичное подключение невозможно восстановить без перезапуска приложения. Отдельной кнопки отмены ввода кода нет.
- **Минимное исправление:** при неуспешном обмене очищать код и сбрасывать `CloudAwaitingCode`, чтобы «Подключить» снова стало доступно.
- **Долгосочное решение:** оформить OAuth как явную конечную модель состояний с командами «Отмена» и «Повторить».
- **Альтернатива:** сохранять `_pending при временном сетевом сбое и разрешать повтор того же кода, но при `invalid_grant` всё равно потребуется сброс; это сложнее и не устраняет необимость восстановления UI.

```csharp
catch (InvalidOperationException ex)
{
    CloudAwaitingCode = false;
    CloudAuthCode = string.Empty;
    _dialogService.ShowWarning(ex.Message);

```

- **Тест:** после отлонённого кода проверить `ConnectYandexCommand.CanExecute(null) == true`, затем выполнить повторное подключение и убедиться, что создан новый verifier.

## **[YD-04] Повреждённая очередь блокирует все новые копии — P1**

- **Расположение:** `AutoKassa/Services/Backup/YandexDisk/YandexDiskBackupService.cs:109-140,378-400`, `AutoKassa/Services/SettingsService.cs:541-565`
- **Уверенность:** высокая.
- **Суть:** если pending-файл существует, он всегда выбирается вместо создания нового ска. При неуспешном `integrity_check` файл сохраняется, поэтому каждая следующая попытка повторяет тот же результат.
- **Сценарий:** сбой записи, запение диска или принудительное завершение оставляет повреждённый `.db`. Все последующие автоматические и ручные запуски останавливаются до сетевой части.
 **Дополнительный фактор:** `CreateBackupAsync` не удаляет частично созданный файл при исключении и превращает любое исключение, включая отмену, в `null`.
- **Посствия:** исходная БД не повреждается, но ключевая функция облачного резервного копирования бессрочно перестаёт работать. Сообщение «Создай новую копию вручную» не решает проблему: следующий облачный запуск снова выберет старый pending-файл.
- **Минимальное исправление:**реждённый файл удалять либо переименовывать в карантин вне активной маски очереди. Это производный снимок, а не исходные данные.
- **Долосрочное решение:** создавать снимок во временный файл, проверять его и только затем атомарно переводить в очередь; при ошибке удалять временный файл и пробрасывать OperationCanceledException`.
- **Альтернатива:** показать пользователю путь и команду «Удалить повреждённую ожидающую копию». Это полезно как UX, автоматическое восстановление всё равно предпочтительнее.

```csharp
if (!await TryVerifyLocalSnapshotAsync(queueFile, ct))
{
    File.Move(queueFile, queueFile + ".corrupt", overwrite: true    return FailWithResult(...);
}
```

- **Тест:** первая попытка получает повреждённый снимок, вторая обязана создать новый файл и успешно дойти до upload Текущий тест `YandexDiskBackupServiceTests.cs:294-313` проверяет только сохранение повреждённого файла и закрепляет нежелательное поведение.

## **[YD-] Ошибки подтверждения метаданных обрабатываются неверно — P2**

- **Расположение:** `AutoKassa/Services/Backup/YandexDisk/YandexDiskBackupService.cs:-291`
- **Уверенность:** высокая.
- **Суть:** `GetResourceBestEffortAsync` перехватывает `YandexDiskApiException`, включая производные `Auth`, `Transient` и `Quota и возвращает `null`.
- **Почему неправильно:** 401 не инвалидирует токен, 5xx/сеть не попадают в retry, квота превращается в «роверка целостности не сошлась».
- **Сценарий:** PUT вернул 201, но последующий GET метаданных получил 500 или 401. Результат — терминаль `Error` вместо `PendingRetry` или `AuthRequired`.
- **Последствия:** неверный статус и сообщение, лишняя задержка восстановления, несоответствие плану обработки ошибок.
- **Минималь исправление:** не перехватывать специализированные исключения в best-effort методе.
- **Долгосрочное решение:** выделить typed `NotFound`; после 201 и 202жидать появление ресурса, а временные ошибки и отсутствие ресурса различать.
- **Альтернатива:** централизовать обработку 401 в API-клиенте Это уменьшит дублирование, но добавит побочный эффект в тонкий клиент; минимальный фильтр в сервисе безопаснее.

```csharp
catch (YandexApiException ex) when (
    ex is not YandexDiskAuthException &&
    ex is not YandexDiskTransientException &&
    ex is not YandexDiskQuotaException)
{
    _log.Warning(ex, "Метаданные ресурсаоступны");
    return null;
}
```

- **Тесты:** 401 и 500 при GET после 201; 401 во время polling после 202; 500 при GET после идемпотентного 409.

## **[-06] `StopAsync` не отслеживает внеочередные задачи — P2**

- **Расположение:** `AutoKassa/Services/Backup/AutomaticBackupService.cs:59-91`, `Kassa/App.xaml.cs:291-312`
- **Уверенность:** высокая.
- **Суть:** `RequestCheck()` создаёт отдельный `Task.Run`, но ссылка на задачу не сохяется. `StopAsync` ожидает только `_timerLoop`.
- **Сценарий:** сохранение настроек запускает длительную проверку, затем пользователь закрывает приложение. Тмерный цикл отменяется и завершается, а внеочередная задача ещё ждёт `_runGate` или выполняет операцию.
- **Последствия:** нарушается гантия плана «не продолжать работу после dispose»; возможны обращения к уже освобождённым зависимостям и незавершённые файловые операции.
- **Минималь исправление:** запретить новые запросы при остановке, отслеживать все request-задачи и включать их в ожидание с общим таймаутом.
- **Долгрочное решение:** один отслеживаемый consumer для всех проверок с coalescing повторных запросов.
- **Альтернативы:** `ConcurrentDictionary<Task>` — небольшоеравление, но требует аккуратного удаления завершённых задач; канал проще для дальнейшего развития, но стоит дороже.
- **Тест:** запустить `Check` с блокирующим `TaskCompletionSource`, вызвать `StopAsync` и убедиться, что он не завершился до освобождения операции. Текущий тест затрагивает толькочу таймерного цикла.

## **[YD-07] Таймаут HTTP считается штатной отменой — P2**

- **Расположение:** `AutoKassa/App.xaml.cs:228 `AutoKassa/Services/Backup/YandexDisk/YandexDiskApiClient.cs:69-80,172-183`, `AutoKassa/ViewModels/SettingsViewModel.cs:888-891`
- **Уверенность:** высок.
- **Суть:** у общего `HttpClient` задано 100 секунд. При истечении таймаута `SendAsync` выбрасывает `TaskCanceledException`, который является `OperationCanceledException`.од безусловно пробрасывает его как отмену.
- **Сценарий:** большая БД или медленная сеть не укладываются в 100 секунд. Retry не выполняется, серис пишет «выгрузка отменена», ручная команда не показывает ошибку.
- **Последствия:** повторяемые неудачи на медленных соединениях и плох диагностируемость.
- **Минимальное исправление:** отличать таймаут от отмены внешним токеном и преобразовывать его в `YandexDiskTransient`.
- **Долгосрочное решение:** подобрать отдельный лимит для загрузки по реальным размерам БД и скоростям; не отключать таймаутностью.

```csharp
catch (TaskCanceledException ex) when (!ct.IsCancellationRequested)
{
    throw new YandexDiskTransientException("Таймаут загрузки.", ex);
}
catch (OperationCanceledException)
{
    throw;
}
```
- **Тест:** fake handler с задержкой больше короткого `HttpClient.Timeout`; внешний токен не отменён. Ожидаются ограниченные retry и `PendingRetry`, а штатная отмена.

## **[YD-08] Запись токена не атомарна — P2**

- **Расположение:** `AutoKassa/Services/Backup/YandexDisk/DpapiYandexTokenStore.cs:83-97`
- **Уверенность:** высокая.
- **Суть:** старый файл удаляется до `File.Move`. Между этими операциями существует окно, в котор сохранённого токена нет.
- **Сценарий:** сбой процесса или ошибка перемещения после `File.Delete`.
- **Последствия:** потеря сохранённого подключения иходимость повторного OAuth. Данные БД не затрагиваются.
- **Минимальное исправление:** при существующем файле использовать `File.Replace(tempPath, _filePath, null)`, ие `File.Move`.
- **Долгосрочное решение:** уникальное имя временного файла и общий небольшой помощник атомарной записи, если такая операция понадобитсящё где-то.
- **Альтернатива:** `File.Move(..., overwrite:true)` убирает явное удаление, но гарантии атомарной замены зависят от платформеннойции; для Windows `File.Replace` точнее соответствует плану.

```csharp
if (File.Exists(_filePath))
    File.Replace(tempPath, _filePath, null);
else
    File.Move(tempPath, _filePath);
```

- **Тест:** через небольшой fault-injection seam симулиать сбой замены и проверить, что предыдущий токен остался читаемым.

## **[YD-09] Локальный сбой пропускает облачную часть — P2**

- **Расположение:** `AutoKassa/Services/Backup/AutomaticBackupService.cs:117-148`, `AutoKassa/Services/SettingsService.cs:651-664,720-740`

- **Сценарий:** ошибка перечисления локальной папки в `GetDaysSinceLastBackup`. Большинство ошибок создания файла внутри `CreateBackupAsync` перехватываются но перечисление находится вне этого `try`.

- **Тест:** локальный сервис всегда выбрасывает исключение; облачный сервис должен быть вызван уже в том же тике. Сующий тест проверяет только восстановление на следующем тике.

# 5. Анализ неоптимальных решений

1. **Использование полного `SettingsService.CreateBackupAsync` как фабрики облачного снимка**
   - Текий подход: метод создаёт снимок, выполняет локальную ротацию, пишет лог и превращает ошибки в `null`.
   - Недостатки: облачная очередьает побочные эффекты локального бэкапа; сложно различать отмену, отсутствие БД и ошибку записи.
   - Рекомендация: после минимального испления YD-04 выделить общий `CreateSqliteSnapshotAsync`, а локальную ротацию оставить вызывающему коду.
   - Польза: ясные ошибки, отсутств лишней ротации, проще тестировать частичные сбои.
   - Стоимость: средняя.
   - Менять сейчас: совместно с исправлением очереди;дельно ради архитектуры не нужно.

2. **Удаление pending-файла до сохранения даты успеха**
   - Расположение: `YandexDiskBackupService.cs:293-307   - Недостаток: если запись даты не удалась, следующий запуск не имеет pending-файла для идемпотентного 409 и создаёт/передаёт новый снимок.
 - Рекомендация: сначала сохранить дату, затем удалить файл очереди. При ошибке даты pending останется и позволит подтвердить тот же cloud-ресурс безторной передачи.
   - Польза: меньше лишних выгрузок при проблемах с БД настроек; лучше восстановление после частичного сбоя.
   - Стоим: низкая.
   - Менять сейчас: да, вместе с YD-04.

3. **Новый `Task.Run` на каждый `RequestCheck`**
   - Недостаток во время долгой загрузки несколько сохранений настроек могут накопить очередь одинаковых проверок.
   - Условия проявления: медленная сеть, retry/тмауты и частые изменения настроек.
   - Рекомендация: coalescing — один запланированный запуск плюс флаг повторной проверки.
   - Эффект: мень лишних операций чтения каталогов, создания снимков и сетевых вызовов.
   - Стоимость: низкая–средняя.
   - Менять сейчас после исправления отслеживания задач в YD-06.

4. **Комментарий о защите статической DPAPI-энтропией**
   - Расположение: `DpapiYandexTokenStore.cs:21-23`.
   - Недостаток: статическая строка находится в приложении и не препятствует другой программе того же Windows-пользователя вызвать Unprotect с той жентропией.
   - Рекомендация: сохранить DPAPI, но исправить threat model в комментарии; новый сложный механизм шифрования не нужен.
   -ольза: отсутствие ложного представления о защите.
   - Стоимость: минимальная.

Явных проблем N+1, чрезмерных выделений памяти или лних вычислений MD5 в цикле нет. Оптимизировать буферы файлового потока или размер страницы без профилирования не рекомендуется.

# 6. Ромендации по улучшению функций

## OAuth и подключение

- **Необходимо:** восстановление повторной попытки после любого неуспешного обмена; сложность низ, риски минимальны.
- **Желательно:** кнопка отмены OAuth и копирование URL; снижает ручную диагностику, сложность низкая.
- **елательно:** сериализовать Disconnect со в активной выгрузкой либо использовать generation token, чтобы старая операция не инвалидировала вновь сохранённый токен; сложность средня, нужен concurrency-тест.
- **Будущая итерация:** оценить loopback redirect вместо ручного ввода кода, если его поддержка подтверждена для выбранного тип приложения Яндекса.

## Очередь и создание снимка

- **Необходимо:** карантин повреждённых файлов и очистка частичных снимков.
- **Желатель:** команда «Удалить ожидающую копию и создать новую» с подтверждением; закрывает постоянный 409 с другим файлом. Риск — удалять только производ файл очереди, не исходную БД.
- **Дополнительно:** показывать имя, дату и размер pending-файла, а также время последней неудачной попытки.
 **Желательно:** интеграционный тест облачной очереди с настоящим `SettingsService`, а не только fake-снимком.

## Выгрузка и ротация

- **Неходимо:** контрактные тесты на реальные JSON-ответы, тип ресурса и классификацию ошибок.
- **Желательно:** единая обработка 401 во всех стадх, включая ротацию, без превращения уже успешной загрузки в неуспешную.
- **Дополнительно:** после подтверждения полезности через замеры ограничить от списка через `fields=_embedded.items.name,...`; эффект заметен только при большом количестве ресурсов.

# 9. Положительные стороны- OAuth/PKCE реализован без встроенного секрета, с правильным ограничением scope и сроком жизни verifier.
- Токены и Authorization-заголовки в проверенном production-ке явно не логируются.
- Используется SQLite Online Backup API, а не копирование активной WAL-базы.
- `Pooling=false` при проверке очереди устраняет известнуюлему удержания файла.
- Загрузка без перезаписи и идемпотентный 409 — удачные защитные решения.
- MD5 используется только для контроля цостности, без ложного заявления о защите от подделки.
- Retry-After, ограниченное число повторов и сохранение очереди соответствуют хорошей практе.
- Singleton `HttpClient`, DI через конструктор и отсутствие Service Locator соответствуют проекту.
- Миграция, дефолты, clone, reset и import/export выполнены сласованно.
- Миграционные тесты используют реальные миграции, а не только `EnsureCreated`.
- Тестовая инфраструктура с HTTP-fakes и `TimeProvider` хошо подходит для дальнейшего развития.
